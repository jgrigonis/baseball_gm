players

CREATE TABLE players (
    id TEXT PRIMARY KEY,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    bats TEXT,
    throws TEXT
);

teams

CREATE TABLE teams (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    league TEXT
);


seasons

CREATE TABLE seasons (
    id TEXT PRIMARY KEY,
    year INTEGER,
    name TEXT      -- e.g. "Season1"
);


series

CREATE TABLE series (
    id TEXT PRIMARY KEY,
    season_id TEXT NOT NULL,
    name TEXT NOT NULL,     -- "Season1ALCS"
    FOREIGN KEY (season_id) REFERENCES seasons(id)
);


games - One row per actual game.

CREATE TABLE games (
    id TEXT PRIMARY KEY,
    date TEXT NOT NULL,          -- ISO date
    season_id TEXT NOT NULL,
    series_id TEXT,
    home_team_id TEXT NOT NULL,
    away_team_id TEXT NOT NULL,

    FOREIGN KEY (season_id) REFERENCES seasons(id),
    FOREIGN KEY (series_id) REFERENCES series(id),
    FOREIGN KEY (home_team_id) REFERENCES teams(id),
    FOREIGN KEY (away_team_id) REFERENCES teams(id)
);


This is where current Stats classes map cleanly.

One row per (player, game).

CREATE TABLE player_game_stats (
    game_id TEXT NOT NULL,
    player_id TEXT NOT NULL,
    team_id TEXT NOT NULL,
    opponent_team_id TEXT NOT NULL,

    -- Batting
    ...

    PRIMARY KEY (game_id, player_id),
    FOREIGN KEY (game_id) REFERENCES games(id),
    FOREIGN KEY (player_id) REFERENCES players(id),
    FOREIGN KEY (team_id) REFERENCES teams(id)
);


Easy aggregation:

SELECT SUM(hits), SUM(home_runs)
FROM player_game_stats
WHERE player_id = ?


team_game_stats - Don’t derive wins/losses from player stats — store them directly.

CREATE TABLE team_game_stats (
    game_id TEXT NOT NULL,
    team_id TEXT NOT NULL,
    runs INTEGER,
    hits INTEGER,
    errors INTEGER,
    win INTEGER,     -- 1 or 0
    loss INTEGER,    -- 1 or 0

    PRIMARY KEY (game_id, team_id),
    FOREIGN KEY (game_id) REFERENCES games(id),
    FOREIGN KEY (team_id) REFERENCES teams(id)
);


Instant standings:

SELECT team_id, SUM(win) AS wins, SUM(loss) AS losses
FROM team_game_stats
GROUP BY team_id;


pitcher_state - This does not belong in game stats, because it evolves between games.

CREATE TABLE pitcher_state (
    player_id TEXT PRIMARY KEY,
    current_energy REAL NOT NULL,
    last_game_date TEXT,
    last_pitch_count INTEGER,

    FOREIGN KEY (player_id) REFERENCES players(id)
);

Typical workflow:

    After each game:

        Reduce energy based on pitch count (this should be done in Game)

    On rest days:

        Recover energy toward max

        Persist once per day or after each game

This table is state, not history — and that’s OK.

def init_db(conn):
    conn.executescript("""

    CREATE TABLE IF NOT EXISTS teams (...);
    CREATE TABLE IF NOT EXISTS games (...);
    CREATE TABLE IF NOT EXISTS player_game_stats (...);
    """)

If a file imports sqlite3, it should live under src/db.

Repositories talk SQL.
Domain objects never do.


If you add a stat to Stats class:

Add it to the table
Add it to the repository
Add a round-trip test

Otherwise you silently lose data.

Keeping DB code isolated gives you:

Headless simulations
In-memory testing
Future UI without refactors
Easy save/load
